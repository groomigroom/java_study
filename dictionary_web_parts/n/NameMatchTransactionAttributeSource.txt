import org.springframework.transaction.interceptor.NameMatchTransactionAttributeSource;는 
스프링에서 "메서드의 이름(Name)을 보고 어떤 트랜잭션 규칙(Attribute)을 적용할지 
결정하는 매핑 지도" 역할을 하는 클래스입니다.
이전 단계에서 만든 RuleBasedTransactionAttribute(전파 방식, 롤백 규칙 등)를 
특정 메서드 이름 패턴에 연결해 주는 가교라고 이해하시면 됩니다.
핵심적인 의미와 동작 방식은 다음과 같습니다.

1. 왜 이 클래스가 필요할까요?

프로젝트를 만들 때 모든 메서드에 똑같은 트랜잭션 규칙을 적용하면 비효율적입니다.
• 데이터를 저장/수정/삭제하는 메서드(insert*, update*, delete*) ➡️ 
쓰기 권한이 필요하고 예외 시 롤백해야 합니다.
• 데이터를 단순히 조회만 하는 메서드(select*, get*) ➡️ 
성능 최적화를 위해 읽기 전용(readOnly = true) 트랜잭션을 주는 것이 좋습니다.
NameMatchTransactionAttributeSource는 바로 이렇게 "이름이 get*으로 시작하는 
메서드는 A 규칙을 쓰고, modify*로 시작하는 메서드는 B 규칙을 써라" 하고 지정을 
해두는 규칙 보관소입니다.

2. 코드로 보는 실제 의미 (조립 과정)

보통 앞서 질문하신 클래스들과 함께 다음과 같은 방식으로 조립되어 사용됩니다.
java
@Bean
public TransactionInterceptor transactionInterceptor(TransactionManager transactionManager) {
    
    // 1. [규칙 A] 쓰기/롤백용 규칙 (앞서 질문하신 코드)
    RuleBasedTransactionAttribute writeAttribute = new RuleBasedTransactionAttribute();
    writeAttribute.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRED);
    writeAttribute.setRollbackRules(Collections.singletonList(new RollbackRuleAttribute(Exception.class)));

    // 2. [규칙 B] 읽기 전용 규칙 (조회 최적화용)
    RuleBasedTransactionAttribute readAttribute = new RuleBasedTransactionAttribute();
    readAttribute.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRED);
    readAttribute.setReadOnly(true); // 읽기 전용 설정

    // 3. [이름 매치 소스] 메서드 이름에 따라 규칙을 매핑하는 지도 생성!
    NameMatchTransactionAttributeSource txAttributeSource = new NameMatchTransactionAttributeSource();
    
    // 💡 핵심: 이름 패턴별로 규칙을 등록합니다.
    txAttributeSource.addTransactionalMethod("insert*", writeAttribute);
    txAttributeSource.addTransactionalMethod("update*", writeAttribute);
    txAttributeSource.addTransactionalMethod("delete*", writeAttribute);
    
    txAttributeSource.addTransactionalMethod("get*", readAttribute);
    txAttributeSource.addTransactionalMethod("select*", readAttribute);
    txAttributeSource.addTransactionalMethod("*", writeAttribute); // 그 외 모든 메서드는 기본 쓰기 규칙 적용

    // 4. 인터셉터에 지도와 일꾼(매니저)을 넘겨줍니다.
    return new TransactionInterceptor(transactionManager, txAttributeSource);
}
코드를 사용할 때는 주의가 필요합니다.

3. 스프링 부트에서의 특징

• AOP를 이용한 공통 트랜잭션의 핵심 수단: 개발자가 서비스 클래스마다 일일이 
@Transactional을 붙이기 귀찮거나, 실수로 누락하는 것을 방지하고 싶을 때 사용합니다.
이 클래스를 이용해 이름 규칙을 짜두면 새 클래스를 만들 때 메서드 이름만 규칙에 
맞게 지어도 트랜잭션이 자동으로 적용됩니다.
• 유지보수의 편의성: 트랜잭션 정책이 바뀌더라도 수백 개의 클래스를 수정할 필요 없이, 
이 설정을 담은 자바 파일 한 곳만 수정하면 되기 때문에 대형 프로젝트의 공통 
설정(수동 AOP 설정)에서 자주 발견됩니다.

지금까지 질문하신 내용 총정리 (AOP 트랜잭션의 퍼즐 조각들)

1. DataSourceTransactionManager: 실제 DB 커밋/롤백을 수행하는 일꾼
2. RuleBasedTransactionAttribute: 어떤 예외 때 롤백할지 정한 지침서
3. NameMatchTransactionAttributeSource: 메서드 이름별로 어떤 지침서를 
볼지 정리한 매핑 지도
4. TransactionInterceptor: 지도(3번)를 보고 메서드를 가로채서, 
지침서(2번)대로 일꾼(1번)을 부리는 총감독


이제 공통 트랜잭션 설정을 위한 핵심 컴포넌트들을 모두 파악하셨습니다. 혹시 이 인터셉터를 적용하기 위해 Advisor나 Aspect를 설정하는 다음 단계 코드도 확인 중이신가요? 아니면 이 방식과 일반 @Transactional 방식 중 어떤 것을 선택할지 고민이신가요? 상황을 공유해주시면 이어지는 고민을 해결해 드리겠습니다.
