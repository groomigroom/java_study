org.springframework.context.ApplicationContext는 
스프링 부트 애플리케이션의 '심장'이자 컴퓨터의 '운영체제(OS)' 
같은 역할을 하는 스프링의 핵심 컨테이너 인터페이스입니다.
스프링 부트가 실행될 때 이 ApplicationContext가 가장 먼저 생성되며, 
애플리케이션 안의 모든 객체(Bean)들을 생성하고, 서로 연결(의존성 주입)해주고, 
생명주기를 관리하는 모든 총괄 책임을 집니다.

💡 핵심 역할과 의미


1. 스프링 빈(Bean)의 공장이자 보관소 (IoC 컨테이너)

개발자가 @Component, @Service, @Repository 혹은 @Bean으로 지정한 
객체들을 생성하여 내부에 보관합니다. 
필요한 곳에 객체를 자동으로 꽂아주는 제어의 역전(IoC)과 
의존성 주입(DI)이 바로 이 객체를 통해 일어납니다.

2. 단순한 빈 팩토리를 넘어선 '종합 인프라 플랫폼'

ApplicationContext는 단순히 객체만 관리하는 구형 BeanFactory 인
터페이스를 상속받아, 실제 서비스 운영에 필요한 수많은 부가 기능을 통합 제공합니다.

주요 기능	설명	관련 메서드 예시
국제화 (i18n)	사용자의 언어(국가) 설정을 인식해 다국어 메시지를 제공합니다.	getMessage()
환경 변수 & 프로퍼티 관리	application.properties 설정값이나 OS 환경 변수를 읽어옵니다.	getEnvironment()
이벤트 발행 및 구독	시스템 내부에서 컴포넌트 간에 신호를 주고받는 이벤트를 처리합니다.	publishEvent()
리소스 조회	파일 시스템, 클래스패스, URL 등 다양한 경로의 자원을 쉽게 로딩합니다.	getResource()


🛠️ 스프링 부트(Spring Boot)에서의 특수성

기본 스프링 프레임워크에서는 톰캣(Tomcat) 같은 외부 WAS 위에서 구동하기 위한 웹 
컨텍스트 설정을 XML이나 자바 코드로 복잡하게 구워내야 했습니다.
반면 스프링 부트는 실행 시점에 애플리케이션 타입을 스스로 판단하여 알맞은 
ApplicationContext 구현체를 자동으로 선택하고 내장 서버를 함께 구동합니다.
• 일반 MVC 애플리케이션: AnnotationConfigServletWebServerApplicationContext가 
생성되어 내장 톰캣을 띄우고 서블릿 환경을 구축합니다.
• 리액티브(WebFlux) 애플리케이션: AnnotationConfigReactiveWebServerApplicationContext가 
생성되어 내장 네티(Netty) 서버를 구동합니다.

🧑‍💻 요약하자면

이전 질문에서 다루었던 ApplicationContextAware, Import, LocalValidatorFactoryBean 
같은 모든 기술과 객체들은 결국 이 ApplicationContext라는 거대한 시스템 안에서 등록되고, 
관리되며, 움직이는 부속품들이라고 이해하시면 됩니다.


지금까지 스프링의 핵심 설정과 컨테이너 구성 요소들 위주로 살펴보았는데, 혹시 이 개념들을 활용해 나만의 프레임워크 확장 
기능(커스텀 라이브러리/스타터)을 만들고 계신가요? 어떤 구조의 코드를 설계 중이신지 공유해 주시면 아키텍처 관점에서 더 자세히 짚어드릴 수 있습니다.

##### Container 객체화 xml 이용

ApplicationContext context = new ClassPathXmlApplicationContext(new String[] {"services.xml", "daos.xml"});

// an Application is also a BeanFactory (via inheritance)
BeanFactory factory = context;

위 예제의 ClassPathXmlApplicationContext는 ApplicationContext의 한 종류이며, ApplicationContext 인터페이스는 BeanFactory 인터페이스를 상속하고 있다.

Container 사용 방법
Container를 객체화하면 getBean(String) 메소드를 사용하여 bean을 가져올 수 있다.

##### ApplicationContext는 Event 처리를 위해 ApplicationEvent, ApplicationListener interface를 제공한다.

ContextRefreshedEvent	
ApplicationContext가 초기화된거나 refresh될 때 발생한다(refresh하기 위해서 ConfigurableApplicationContext interface의 refresh() 메소드를 사용한다). 
“초기화”라는 단어는, 모든 bean이 load되었고, post-processor bean이 탐지되어 활성화되었으며, singleton 객체가 선객체화되어, 
ApplicationContext 객체가 사용가능한 상태에 있다는 것을 의미한다.
refresh는 context가 닫혀지지 않은 한, 여러번 발생할 수 있으며, 
ApplicationContext가 “hot” refresh를 지원해야한다 
(XmlWebApplicationContext는 “hot” refresh를 지원하지만, GenericApplicationContext는 지원하지 않는다).

ContextStartedEvent	ApplicationContext가 시작될 때 발생한다(시작하기 위해서 ConfigurableApplicationContext interface의 start() 메소드를 사용한다). “시작됨(Started)“이란 단어는, 모든 Lifecycle bean이 명시적인 시작 신호를 받았음을 의미한다. 이 event는 일반적으로 명시적인 정지(stop) 후에, 재시작하기 위해서 사용되지만, 자동시작(autostart)로 설정되지 않은 컴포넌트를 시작하기 위해서도 사용된다
ContextStoppedEvent	ApplicationContext가 정지할 때 발생한다(정지하기 위해서 ConfigurableApplicationContext interface의 stop() 메소드를 사용한다). “정지됨(Stopped)“란 단어는, 모든 Lifecycle bean이 명시적인 정지 신호를 받았음을 의미한다. 정지된 context는 start() 호출을 통해 재시작될 수 있다.
ContextClosedEvent	ApplicationContext가 닫혔을 때 발생한다(닫기 위해서 ConfigurableApplicationContext interface의 close() 메소드를 사용한다). “닫힘(Closed)“란 단어는, 모든 singleton bean이 파괴되었음을 의미한다. 닫힌 context는 생명주기의 끝에 도달한 것으로, refresh 되거나 재시작될 수 없다.
RequestHandledEvent	웹에 특화된 event로서, HTTP request가 처리되었음을 알린다(request가 종료된 후에 발송된다). Spring의 DispatcherServlet를 사용하는 웹 어플리케이션인 경우에만 사용할 수 있다.
