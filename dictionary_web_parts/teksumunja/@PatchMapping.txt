스프링 부트(Spring Boot)에서 @PutMapping과 @PatchMapping은 HTTP 메서드인 PUT과 PATCH를 각각 처리하며, 리소스(데이터)를 수정할 때 사용하지만 수정 방식과 
의미론에서 차이가 있습니다. [1] (https://www.youtube.com/watch?v=NTPxSex_jEc&t=1), [2] (https://post-this.tistory.com/127), 
[3] (https://www.inflearn.com/community/questions/1182007/patch%EC%99%80-put%EC%9D%98-%EC%B0%A8%EC%9D%B4%EC%A0%90?srsltid=AYCX9vIs0pzSZ_r-dQhbByux6QVe56VV5sLZ3tHOAa0VjnWDGVJ-qKTj)

1. @PutMapping (PUT 방식)

• 역할: 리소스의 전체 수정 및 완전 대체 (Full Update) [1] (https://rameshfadatare.medium.com/difference-between-patchmapping-and-putmapping-in-
spring-boot-6713a62d6cf4), [2] (https://ycyeon.tistory.com/145)
• 동작 방식:
	• 전달한 데이터로 기존 자원을 완전히 교체합니다.
	• 요청 데이터에 포함되지 않은 필드가 있다면, 해당 필드는 null이나 기본값으로 덮어씌워질 위험이 있습니다.
	• 따라서 @PutMapping을 사용할 때는 보통 리소스의 모든 필드값을 요청 본문(Body)에 담아 보내야 안전합니다. [1] (https://www.youtube.com/watch?v=8wElweV
  GsqE&t=1), [2] (https://post-this.tistory.com/127), [3] (https://ycyeon.tistory.com/145), [4] (https://rameshfadatare.medium.com/difference-between-patchmapping-and-putmapping-in-spring-boot-6713a62d6cf4)
• 멱등성(Idempotency): 보장됨 (O) — 동일한 요청을 여러 번 반복해서 보내도 서버의 상태가 동일하게 유지됩니다. [1] (https://post-this.tistory.com/127
), [2] (https://ycyeon.tistory.com/145)

2. @PatchMapping (PATCH 방식)

• 역할: 리소스의 부분 수정 (Partial Update) [1] (https://rameshfadatare.medium.com/difference-between-patchmapping-and-putmapping-in-spring-boo
t-6713a62d6cf4), [2] (https://ycyeon.tistory.com/145), [3] (https://okky.kr/questions/1493377)
• 동작 방식:
	• 전달한 일부분의 필드만 수정합니다.
	• 요청에 포함되지 않은 나머지 필드들은 기존 값 그대로 유지됩니다. [1] (https://rameshfadatare.medium.com/difference-between-patchmapping-and-pu
  tmapping-in-spring-boot-6713a62d6cf4), [2] (https://okky.kr/questions/1493377), [3] (https://www.youtube.com/watch?v=8wElweVGsqE&t=1)
• 멱등성(Idempotency): 구현 방식에 따라 가변적 (△) — 단순히 값을 특정 값으로 고정해 바꾸는 경우는 멱등성이 성립하지만, '기존 값에서 +1 증가' 
같은 연산이면 요청할 때마다 값이 계속 바뀌어 멱등성이 성립하지 않을 수 있습니다. [1] (https://ycyeon.tistory.com/145)

3.지요약 비교표


구분	@PutMapping	@PatchMapping
수정 범위	전체 리소스 대체 (Full Update)	일부 리소스 수정 (Partial Update)
요청 데이터	객체의 모든 필드 필요	수정할 필드만 전송 가능
미전달 필드 처리	null 또는 기본값으로 초기화될 위험 있음	기존 데이터 그대로 유지됨
HTTP 멱등성	보장됨 (O)	구현에 따라 다름 (△)

프로젝트에서 어떤 엔티티(예: 회원 정보, 게시글 등)를 수정하려고 하시나요? 전체 교체가 필요한지, 아니면 비밀번호나 닉네임처럼 
특정 값만 바꾸고 싶은지 알려주시면 알맞은 구현 방식을 추천해 드릴 수 있습니다.
