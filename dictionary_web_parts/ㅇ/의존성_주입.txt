private final ProductService productService;

public ProductController(ProductService productService) {
  this.productService = productService;
} 

자바 스프링에서 위와 같은 코드 구조를 뭐라 하나?


자바 스프링 프레임워크에서 위와 같은 코드 구조를 생성자 주입 (Constructor Injection)이라고 부릅니다.
이는 스프링의 핵심 개념인 의존성 주입(DI, Dependency Injection)을 구현하는 방법 중 하나이며, 현재 스프링 공식 진영에서 가장 강력하게 권장하는 표준 방식입니다.
이 구조의 특징과 장점을 쉽게 정리해 드립니다.
## 1. 왜 '생성자 주입'인가요?
ProductController라는 객체가 생성될 때, 스프링 컨테이너가 자신이 관리하던 ProductService 객체를 생성자의 매개변수로 직접 꽂아 넣어주기(주입) 때문에 붙여진 이름입니다.
## 2. 이 구조의 핵심 장점
과거에는 @Autowired 어노테이션을 필드에 바로 붙이는 '필드 주입' 방식을 많이 썼지만, 최근에는 모두 생성자 주입으로 넘어왔습니다. 그 이유는 다음과 같습니다.

* NullPointerException(NPE) 방지: 객체를 생성하는 시점에 의존성(ProductService)이 무조건 주입되어야만 컴파일이 되므로, 서비스 객체가 누락되어 발생하는 런타임 에러를 원천 차단합니다.
* 불변성 보장 (안정성): 필드에 final 키워드를 사용할 수 있습니다. 한 번 주입된 서비스 객체는 애플리케이션이 실행되는 동안 절대로 변경되거나 다른 객체로 대체될 수 없어 코드가 매우 안전해집니다.
* 테스트 용이성: 순수한 자바 테스트 코드를 작성할 때, 스프링 컨테이너를 굳이 켜지 않고도 new ProductController(mockService)와 같이 개발자가 직접 가짜(Mock) 객체를 생성자로 주입하여 독립적인 유닛 테스트를 쉽게 수행할 수 있습니다.

## 💡 보너스 팁: 롬복(Lombok)을 활용한 더 간단한 표현법
만약 프로젝트에 Lombok 라이브러리가 설정되어 있다면, 아래와 같이 @RequiredArgsConstructor 어노테이션을 클래스 상단에 붙여서 이 생성자 코드를 완전히 생략할 수 있습니다.

@Controller
@RequestMapping("/products")
@RequiredArgsConstructor // 👈 final이 붙은 필드를 모아 생성자를 자동으로 만들어줍니다.public class ProductController {

    private final ProductService productService;

    // 생성자 코드를 직접 작성하지 않아도 위와 똑같이 '생성자 주입'으로 동작합니다.
}
