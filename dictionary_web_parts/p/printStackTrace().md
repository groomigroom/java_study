자바 스프링 부트(Spring Boot) 환경에서 catch 블록 내의 e.printStackTrace();는 "에러가 발생한 지점과 그 지점까지의 메서드 호출 흐름(Stack Trace)을 콘솔(표준 에러 스트림, System.err)에 그대로 출력하라"는 의미입니다.
로컬 환경에서 개인 토이 프로젝트를 개발할 때는 에러를 빠르게 확인하는 데 도움이 되지만, 실무 스프링 부트 애플리케이션에서는 절대로 사용해서는 안 되는 금기 코드 중 하나입니다.
그 구체적인 이유와 대안을 정리해 드립니다.
------------------------------
## 1. 스프링 부트에서 e.printStackTrace()의 문제점

* 로그 관리 시스템(Logback 등)의 통제를 벗어남
* 스프링 부트는 기본적으로 Slf4j와 Logback이라는 강력한 로깅 라이브러리를 사용합니다. 이를 통해 로그를 파일로 저장하거나, 날짜별로 분리하고, 특정 레벨(INFO, ERROR)만 골라서 볼 수 있습니다.
   * 하지만 e.printStackTrace()는 로그 시스템을 거치지 않고 서버 콘솔에 생으로 글자를 찍어버립니다. 이 때문에 파일로 저장되지 않고 유실되거나, 분석 시스템(ELK, AWS CloudWatch 등)에서 에러 로그로 인식하지 못합니다.
* 서버 성능 저하 (성능 병목)
* e.printStackTrace()는 내부적으로 System.err를 사용하는데, 이는 동기(Synchronous) 및 블로킹(Blocking) 방식으로 작동합니다.
   * 즉, 수많은 사용자가 접속하는 운영 서버에서 에러가 발생해 이 메서드가 호출되면, 로그를 콘솔에 다 출력할 때까지 애플리케이션의 다른 스레드들이 멈추거나 느려지는 심각한 성능 저하가 발생합니다.
* 보안 취약점 발생
* 스택 트레이스에는 내부 클래스명, 메서드 구조, 사용 중인 라이브러리 버전 등이 고스란히 노출됩니다. 만약 콘솔 로그가 외부로 유출되거나 에러 페이지에 그대로 노출될 경우, 해커에게 시스템 구조를 가르쳐주는 꼴이 됩니다.

------------------------------
## 2. 스프링 부트에서의 올바른 대안: log.error()
스프링 부트에서는 e.printStackTrace() 대신, 클래스 상단에 @Slf4j 어노테이션(Lombok 제공)을 붙이고 log.error()를 사용해야 합니다.

@Slf4j
@Servicepublic class UserService {

    public void registerUser(UserDto dto) {
        try {
            // 회원가입 로직 (예: DB 저장)
        } catch (DataIntegrityViolationException e) {
            
            // ❌ 나쁜 예시: 성능을 갉아먹고 로그 유실 위험이 있음
            // e.printStackTrace(); 

            //  올바른 예시: 로그 프레임워크를 통해 안전하게 기록
            // 첫 번째 인자에는 에러 설명 문자열을, 두 번째 인자에는 예외 객체(e)를 그대로 넘깁니다.
            log.error("회원가입 중 데이터 무결성 위반 발생: {}", dto.getEmail(), e);
            
            throw new CustomException("이미 존재하는 이메일입니다.");
        }
    }
}

## 💡 핵심 팁
log.error("에러 메시지", e);와 같이 마지막 인자에 {} 없이 예외 객체 e를 그대로 던져주면, 로그 프레임워크가 스택 트레이스를 안전하고 보기 좋게 포맷팅하여 로그 파일에 기록해 줍니다. (e.getMessage()만 찍으면 전체 에러 흐름을 볼 수 없으니 반드시 e 전체를 넘겨야 합니다.)
